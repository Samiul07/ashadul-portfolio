# Design Language & UI/UX

- Any redesign of a section must be based on the design language already established on the homepage or portfolio page — the user explicitly requires reusing existing site patterns (portrait frame treatments, type scale, overline labels, red accents, hairline borders) rather than inventing a new look. Confidence: 0.9
- When asked for a redesign, expects the agent to speak/act as a UI/UX design expert and come up with the creative direction itself — do not ask for permission at every step. Repeatedly hands over creative freedom explicitly ("I'm giving you creative freedom") and expects it to be exercised, not handed back as options. Confidence: 0.85
- Considers nested/redundant framing ("box in a box" — a card with its own bordered box inside a section that is already framed) and decorative over-styling (glow shadows, chamfered corners, code-style prefixes like `//` on editorial text) as over-engineered and to be stripped out in favor of clean editorial layouts. Confidence: 0.8
- Dislikes unbalanced section compositions where one column is content-heavy and the other side is largely blank — dead horizontal space makes a layout read as unfinished ("someone left it at 70%"); expects content to fill the available frame width/height (full-width text, anchored bottom rows) so the section feels complete and balanced. Confidence: 0.85
- When a section has dead space, prefers filling it with supporting content drawn from the site's existing component language (stat/quick-facts grids from the portfolio hero, social link rows from the footer) rather than leaving it empty or padding it out. Confidence: 0.8
- Treats color as part of the house style: dim/translucent variations of the site's colors (faint gray social buttons, low-opacity white labels at white/55-60) are flagged as broken ("fix the colors man!") — expects the exact established treatments (solid white social circles with black icons, signature red `#ff1e00` for accents, readable labels at white/70-75) rather than re-invented or muted versions. Confidence: 0.8
- Explicitly dislikes high cognitive load in section design: a busy section full of competing cards and dense metadata is called "very, very busy... too much cognitive load" and "could be done much better" — expects calm, low-density layouts with a single clear recommendation/primary action and minimal metadata per item. Keeps pushing on this even after simplification: a section that is visually clean but stacks too much information (featured card + numbered list + CTA panel together) is still rejected ("too much information in one specific section") — one section should do one thing, one clear pattern repeated (e.g., header + simple numbered list), simple and visually good at the same time. Confidence: 0.9
- Treats a feature placed in the wrong section as a mistake: when the user explicitly specifies where something belongs (e.g., the "message the author" option inside the author/about-the-author section), place it there exactly — dropping it into a different section (like the continue-reading/Explore More area) draws an immediate correction. Confidence: 0.8
- For "more reading" / "Explore More" sections, plain text-only lists feel unfinished to the user — they expect a "you might like" recommendation pattern with visual previews: small thumbnails per recommendation (a small multiple grid of 2–3 cards, thumbnail on top with category chip, title below), not prev/next navigation and not bare text rows. The exact layout is delegated to the agent's creative judgment. Confidence: 0.85
- When redesigning a section, the section should stay simple/low-cognitive-load AND visually rich — the user pushes back on the opposite failure modes: too many competing elements (featured card + list + CTA panel) OR a stripped-down version that reads as "just basic text"; the sweet spot is one repeated pattern that includes visual content (e.g., thumbnail cards), not text alone. Confidence: 0.8
- Wants section content to be contextually logical and dynamic: "previous" navigation only makes sense when a previous item actually exists — on the newest post (no predecessor), curated recommendations should replace dead prev/next slots rather than showing nonsense or duplicates. Confidence: 0.85
- Buttons must be unified into ONE house style taken from the homepage hero primary button (chamfered top-left/bottom-right 45° cuts, ~52px height, font-sans sentence-case text with the ArrowUpRight icon; smaller utility buttons keep the same chamfer at a reduced height) — seeing "different types of button" across a page is called "definitely wrong," and every button on a page must be updated to the homepage/hero button spec, not left with per-section variants (uppercase overline pills, rounded rectangles). Confidence: 0.9
- Typography is part of the design language: section titles, card titles, and numerals on any page must follow the site's established type scale and display language (Big Shoulders display sizes with tight tracking and the red period, card titles at the homepage note-card size, etc.) as set by the homepage/landing page — text sizes and internal spacing that differ from the established scale are flagged as "entirely different" and must be aligned rather than improvised per section. Confidence: 0.85
- Cards on sub-pages must replicate the homepage card anatomy exactly (same image aspect ratio, gradient overlay, category chip treatment, title size, and hover states) rather than a simplified lookalike — a card block that doesn't look like the homepage card itself is explicitly called out as breaking the design language. Confidence: 0.85
- When the user flags a design-language inconsistency, they expect a thorough audit of EVERYTHING previously touched (all buttons, titles, spacing, and cards across the sections the agent worked on) with every deviation fixed to match the established design language — not just the single element mentioned ("check every single thing to confirm, come back and update every single thing that you have touched so far in terms of UI"). Confidence: 0.9
- Avoids repeating the same icon everywhere: seeing the same arrow icon on every button is called out ("why the fuck every single icon is arrow icon?"). Icons must be semantically purposeful — navigation arrows only on actual navigation links, a distinct icon for copy actions (chain-link), and no arrow on a form submit like Subscribe. Confidence: 0.9
- Chamfered corners must have complete, connected stroke outlines: a CSS `border` + `clip-path` renders broken/cut-off strokes at the chamfered corners, which is flagged as missing; the correct treatment is the homepage's custom SVG stroke path that traces the chamfer outline (`stroke="currentColor"`, `vectorEffect="non-scaling-stroke"`), so ghost/secondary buttons keep a continuous stroke. Confidence: 0.85
- Prefers direct reuse of existing components over re-implementing approximations: when a block/section already exists elsewhere on the site (e.g., homepage note cards), the user says to "just copy the three blocks directly from home screen... take it directly from there" — import and reuse the actual component so hover effects, spacing, and look are identical by construction rather than re-created ("why bother?"). Confidence: 0.9
- Expects every UI detail (button text font/size, icon choice, stroke edges) to be confirmed and re-confirmed for consistency — "every single thing, the icon, everything needs to be confirmed and confirmed"; when the user is unsure whether elements match (same font? same size? consistent icons?), verify and confirm the consistency rather than leaving it ambiguous. Confidence: 0.85
- All elements stacked within a section (overline label, section heading, content blocks/cards) must align to the same left edge — leftover inline padding that pushes one element (e.g., a heading) right of its label and content is flagged as broken and must be removed so everything shares the section's frame padding. The user re-checks and re-flags the same element ("still not same for the more notes text") until the left edges match exactly; if the code is already pixel-aligned, verify in the real rendered browser and rule out stale dev-server/browser renders before declaring it fixed. Confidence: 0.95
- Left-edge alignment must be judged by the *visible ink* of the glyphs, not the element's layout box: even when `getBoundingClientRect` reports identical positions, a large display-font heading (e.g., Big Shoulders at 160px) has internal left side-bearing that starts its first letter several pixels right of smaller labels set in a different font (Switzer) — the user keeps flagging this as "still not the same" until the rendered ink is actually flush. Fix by an optical nudge (e.g., `-ml-[8px]` on the heading) and prove it by scanning the actual rendered pixel positions per text row rather than trusting DOM/vision-model measurements. Confidence: 0.9
- Contextual scoping for progress/loader UI: the mobile reading bar must stay hidden over the hero and only appear once the reader has actually entered the article reading area (as the Key Takeaways box crosses mid-viewport), then start counting from there — and it should disappear once the article reading area is fully scrolled past. A progress bar sitting on screen where it doesn't yet apply (on page load over the hero) is called out as a bug, not a feature. Progress must also be scoped to the content it measures: it should reach 100% exactly when that content (the article) is done reading and stay pinned at 100% through trailing page sections (e.g., More Notes) rather than keep creeping up with whole-page scroll. Confidence: 0.9
- Dislikes abrupt/sudden appearance of UI elements (e.g., a bar that "comes all of a sudden" with no motion): expects smooth, simple entry/exit animation — a slide (translateY) with fade and a gentle easing — whenever an element appears or disappears, rather than it popping in/out instantly. Confidence: 0.9
- Parallel/sibling section headings must share identical responsive sizing at every breakpoint: when one section's title (e.g., Collab Notes) has a mobile size that differs from a sibling's (More Notes), the user flags the mismatch and asks to copy the established one's exact mobile size/leading/tracking — scoped only to the affected breakpoint, leaving desktop sizes untouched. Confidence: 0.85
- Action hierarchy must be tiered and unmistakable: one primary action (solid button) as the single focal point, a secondary action as a stroked/bordered button, tertiary as quiet text, and the least important options (email/social) muted — options may all exist, but they must never read as equal-weight buttons in a row ("which one do I look at?"). Multiple same-styled buttons side by side are explicitly rejected; the primary action's dominance must be maintained. Confidence: 0.85
- Section title grammar must not invent supporting copy: the established site pattern is overline → display title with no subtitle; adding an explanatory paragraph under a section title is flagged as breaking the design language ("no section title has a subtext — why did you add one?"). Confidence: 0.9
- Interactive elements must reuse the site's established motion language: e.g., the FAQ accordion's hover-expand speed and easing must match the homepage "How I Can Help" section's expansion rhythm exactly — an animation that feels different on a similar interaction is called out and must be aligned, with the active row allowed to switch to the red accent. Confidence: 0.85
- Numeric indices on sections/rows (01, 02…) should use the site's display typeface treatment; small sans utility numerals are rejected as a bad font choice for numbers and must be changed. Confidence: 0.7
- Adjacent sections must read as distinct chapters, not one continuous box: keep real breathing space between them and avoid shared continuation of frame lines/crosshairs that glues sections together — a hero glued to the next section with zero gap and connected lines is called "box-on-box" garbage. Confidence: 0.85
- Text overlaid on photos should sit on a shallow bottom-up gradient fade (just enough contrast to stay legible, fading into the image) rather than a solid dark panel or thick backdrop blur — a visible dark "box" under portrait text is explicitly disliked. Confidence: 0.75
- Prefer a single gradient background that extends naturally across adjacent sections; stacking a separate background per section (e.g., a distinct one on the logo strip) is wrong — only one background should rule, and how far it reaches follows the gradient itself. Confidence: 0.7
- Oversized display wordmarks must never be clipped: full glyph tops (e.g., S, D of "ASHADUL") must remain visible, with the blur fade applied so the mark sits cleanly at the page bottom with proper spacing below the framed content. Confidence: 0.7
- Mobile layout conventions: buttons stack full-width with consistent height and internal spacing, and hero compositions should dynamically fit the available browser viewport height when that pattern is already in use. Confidence: 0.8
- When two UI elements share the same boundary edge (e.g., a red scroll-progress bar and a 1px white divider line both at the header's bottom), they must be layered so the heavier accent overlays the base line along one clean seam — not positioned so they render stacked/side-by-side. The user flags side-by-side rendering as a bug and expects a fix that both aligns the geometry flush to the shared edge and raises the accent's z-order above the base line (verified at every affected breakpoint). Confidence: 0.8
- Fixed overlay elements that belong to a top-anchored fixed header (e.g., a scroll-progress bar that must ride with the navbar) must be positioned from the **top** with offset math — `top = header height − element height` (e.g., `top-[83px]` for a 3px bar in an 86px header, so the bar's bottom edge lands exactly on the header's bottom seam). Never use `bottom-[calc(...)]` for such an element: bottom-anchoring pins it to the viewport bottom and it floats at the screen's edge while scrolling. The user caught this exact bug after a claimed fix and reacted angrily; the corrected approach keeps the element traveling with the header and must be verified both in the actual rendered screenshot and in the served HTML at every affected breakpoint before declaring done. Confidence: 0.8
- A fixed-header overlay must also be z-indexed **above the header itself**, not merely above the base line it overlays: the header's semi-transparent surface layer renders over any element with a lower z-index, so once the overlay is tucked inside the header's bounds it becomes completely invisible (the progress bar vanished entirely at `z-[302]`/`z-[21]` under a `z-[1100]` header; raising it to `z-[1101]` made it visible again). When such an overlay disappears after a geometry fix, check stacking context before re-guessing position, and confirm the elevated z-index in the served HTML before declaring done. Confidence: 0.8
- The user judges UI by **perceived visual weight, not code values**: after a geometry fix, an element that reads visually heavier than before is flagged ("have you made it thicker than it used to be?") even when its dimensions were never changed — e.g., the 3px red progress bar sitting flush on the 1px white divider now reads as a solid 3px line. When asked whether a dimension changed, verify against the actual code and answer directly; if it was never changed, reduce the dimension (e.g., to 2px) to restore the original slimmer feel while keeping geometry aligned (adjust the top offset so the bottom edge stays flush on the shared seam). Confidence: 0.8
- Scroll-reveal (lazy-load) animations must trigger **the moment content enters the viewport** — "whenever it enters the viewport, reveal it with a light lazy-loading animation" — never after the user has scrolled far past it. Revealing an element only once it has been fully scrolled above the viewport (a "scrolled-past" fallback in the IntersectionObserver, e.g., `boundingClientRect.bottom < 0`) is called out as a bug; the trigger should be viewport entry (`isIntersecting`), and reveal should unobserve after firing. Confidence: 0.9
- Decorative background gradients that bleed outside their own section (e.g., a CTA/footer gradient container with `top-[-400px]` plus a tall mobile gradient asset) must stay on the lowest background layer and never render over adjacent content — the user flags the gradient overlapping the last project card on mobile as a bug and requires it to always sit behind everything ("never comes over anything else"). The fix is placing the gradient container at a negative z-index (`-z-10`) within its wrapper's stacking context; because the element is shared across pages (footer on home/portfolio/blog/contact), the corrected layering must hold on every page, not just the reported one. Confidence: 0.7
